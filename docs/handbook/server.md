# Server diagnostics & operations

**Server** and **Workload** organize live diagnostics and administration around the connection in use:

- **Server** groups ten views into five categories: **Overview** (**Health**, **InnoDB**, **Error log**), **Contention** (**Locks**), **Schema** (**Indexes**, **Tables**), **Setup** (**Parameters**, **Instruments**, **Maintenance**), and **Security** (**Users and roles**).
- **Workload** groups five views into two categories: **Queries** (**Top statements**, **Processlist**) and **Resources** (**Memory**, **Waits**, **I/O**).
- **Tuning** scores the checks that **Health**, **Parameters**, **Tables** and **Full analysis** evaluate, and runs **Full analysis** in its own tab.
- **Topology** sits after **Workload** and shows a whole **Group connection** (its map, members, and how parameters, accounts and plugins differ) with a rolling parameter change; see [Read a whole group in Topology](howto-topology.md#read-a-whole-group-in-topology) and [Change a parameter on every server](howto-topology.md#change-a-parameter-on-every-server).
- **Replication**, **Cluster**, **ProxySQL** and **Readyset** follow in the sidebar as dedicated topology and operations places.

Opening any view only reads. Every action that changes server state, kills a session, modifies an index or table, changes a parameter or instrument, runs a maintenance tool, skips a replication transaction, switches a cluster role, or updates ProxySQL or Readyset opens a review sheet first, shows the exact SQL or command it will run, checks the connection's write policy (**Production**, **Development** or **Read-only**), re-verifies the target right before sending, and records the outcome in the local **Audit** log. For host-level SFTP browsing and SSH key management, see [File transfer and SSH](files.md).

In **Server** and **Workload**, **Refresh** reads the active view. Opening **Refresh options** (the menu beside **Refresh**) and choosing **Refresh every view on `<connection>`** (**⌥⌘R** on macOS, **Alt+Ctrl+R** on Windows and Linux) refreshes the **Server** and **Workload** views, **Replication**, **Cluster**, and **Database diagram** (when a database is selected; an imported diagram file is left as is) up to three at a time, then runs **Full analysis** in a second phase so its sampling window does not compete with the other reads. **Maintenance** refreshes client-tool detection only, and **Audit** stays local. While a refresh is running, **Stop** (or **Esc**) cancels the remaining reads and keeps any results that already arrived.

Each report stays bound to the connection it was read from. When you switch to another saved connection, an existing report from the previous connection stays visible in a dimmed state with its server actions disabled until you refresh on the new connection.

For step-by-step walkthroughs, see the [Server and workload how-to guides](howto-server.md), [Connections and files how-to guides](howto-connections.md), and [Replication, clusters and proxies how-to guides](howto-topology.md).

## Health

**Server** > **Health** samples `GLOBAL STATUS` twice over a short window alongside `GLOBAL VARIABLES`, InnoDB metrics and connection counts to show throughput, latency pressure, buffer pool efficiency and capacity limits.

- **What you see**: a status summary, **Live charts** (**Queries per second**, **Threads running**, **Buffer pool reads from disk per second**, **Connections in use**) that keep up to 60 samples in memory for the current connection, **Diagnostics** grouped by severity (**Problem** and **Watch**), and metric tile groups for throughput, InnoDB buffer pool and redo, temporary tables, joins and sorts, connections, and replication. Selecting any diagnostic or tile opens the inspector with its measured numbers, rule of thumb, relevant settings, suggested SQL or option-file lines to copy, and links to **Learn** lessons or related views. Diagnostics for full table scans or joins without an index include a **Statements behind it** section where **Show statements** loads the responsible Performance Schema digests and **Open in Top statements** jumps to **Workload** > **Top statements** sorted by that counter.
- **Controls**: **Window** sets the two-snapshot sampling interval (**1 s**, **2 s**, **5 s** or **10 s**). **Auto-refresh** offers **While visible** (the default on both **Production** and **Development** connections, waiting one **Window** interval after each completed read and remembered per connection **Type**), **Off**, **Every 10 s**, **Every 30 s** and **Every 60 s**; auto-refresh pauses while the view, window or tab is hidden, while another read is in flight, or while another connection's dimmed report is on screen until **Refresh**.
- **Baselines**: open **Refresh options** (the chevron beside **Refresh**) and choose **Save baseline…** to store the current `Health` report on this computer for that server (`server_uuid` on MySQL, or `hostname:port` on MariaDB). Choose **Compare with baseline…** to line the current report up against a saved baseline; the comparison bar shows the baseline's name and timestamp with **Change…** and **Stop comparing**, and each metric tile and inspector shows the baseline value and percentage delta when the sampling windows are within 2x of each other.
- **Incident capture**: **Capture when…** watches the server on a timer without changing server state and captures a single JSON bundle (`incident-capture-1.0`: **Health**, **Processlist**, **Locks** and **InnoDB**) as soon as any threshold you checked fires: **Threads running at or above**, **A row lock wait older than**, or **A statement running longer than**, checked every **Check interval** (from 2 s to 60 s). When **Stop after the first capture** is checked, watching stops after the first bundle downloads; otherwise it continues up to 10 captures with a 30 s cooldown. After a capture, **Open investigation** loads the bundle into **Plans** > **Investigations**, and **Start** (or **Start again**) / **Stop** controls the watcher.
- **Actions**: **Health** performs no server writes. Suggested `SET PERSIST` or `SET GLOBAL` statements in the inspector are for you to copy or open in the **Query editor**.
- **Engine and privilege notes**: reads `SHOW GLOBAL STATUS` and `SHOW GLOBAL VARIABLES`. InnoDB buffer pool and redo details use `information_schema.INNODB_METRICS` where available; statement attribution requires `SELECT` on `performance_schema.events_statements_summary_by_digest`.

## InnoDB

**Server** > **InnoDB** parses `SHOW ENGINE INNODB STATUS` into structured sections so you can inspect internal engine state without reading a raw text dump.

- **What you see**: a summary strip (snapshot timestamp, sample window, history list length, row lock waits, log sequence number, checkpoint age, buffer pool size and hit rate, and semaphore waits), followed by sections for transactions and purge, row operations, buffer pool and memory, log and checkpoints, semaphores, and latest foreign key or deadlock notices when present. Selecting a metric or section opens the inspector with its explanation and thresholds. **Every parsed number** expands the complete key-value table extracted from the snapshot, and **Show raw output** at the bottom reveals the verbatim `SHOW ENGINE INNODB STATUS` text.
- **What it answers**: whether purge is falling behind (`History list length`), how far the last checkpoint sits behind the current LSN, whether threads are spinning or waiting on internal rw-locks or mutexes, and what the last foreign key error or deadlock recorded.
- **Actions**: read-only.
- **Engine and privilege notes**: requires the `PROCESS` privilege on MySQL, Percona Server and MariaDB. When the account lacks `PROCESS`, a prerequisite gate shows the exact `GRANT PROCESS ON *.* TO ...;` statement to run.

## Error log

**Server** > **Error log** reads recent server error, warning, note and system messages so you can correlate restarts, crashes, InnoDB recovery notices and access errors with workload symptoms.

- **What you see**: a summary strip with total entries, error and warning counts, and the source (`performance_schema.error_log` or the local log file path), plus a table of log events (`Timestamp`, `Level`, `Code`, `Subsystem`, `Message`) or grouped error codes (`Code`, `Level`, `Subsystem`, `Count`, `Last seen`, `Sample message`). Selecting a row opens the inspector with the full message, timestamp, thread ID, error code, subsystem, and explanations for common error codes.
- **Controls**: switch between **Entries** and **By code**, filter by level (**All**, **Errors**, **Warnings**, **Notes**, and on MySQL **System**), choose a **Time** window (**All time**, **Last hour**, **Last 6 hours**, **Last 24 hours**, **Custom range**), search with **Filter error log**, or check **This run only** to hide entries written before the server's current uptime started. **Export** downloads the filtered view as **CSV**, **Log (.log)** or **JSON**.
- **Actions**: read-only.
- **Engine and privilege notes**: MySQL 8.0.22 and later reads `performance_schema.error_log` over the connection (requiring `SELECT` on that table). On MariaDB (which has no `performance_schema.error_log` table; `sql_error_log` is a write-only audit plugin), MySQL 5.7, and MySQL 8.0 before 8.0.22, myflames reads the error log file directly when the server is on the same computer and the file path in `@@log_error` is readable, or shows the resolved `@@log_error` path and command-line viewing guidance when connected to a remote host or when `log_error` is `stderr`.

## Locks

**Server** > **Locks** shows active row-lock waits, metadata-lock (MDL) waits, open InnoDB transactions, blocking trees and the latest recorded InnoDB deadlock.

- **What you see**:
  - **Waiting DDL** at the top whenever a DDL statement is blocked on a metadata lock or row lock, naming the blocked statement, the blocking session, its transaction age, and what to end.
  - **Blocking tree**, grouping chains of blockers and waiters so the root blocker sits at the top with the sessions waiting behind it.
  - Four **Show** tabs: **Transactions** (open InnoDB transactions with state, age, tables locked, row locks, modified rows and isolation level), **Row locks** (held and waiting data locks with a **Table** filter), **Metadata locks** (held and pending MDL locks with object type, schema, name, lock type and duration), and **Latest deadlock** (the parsed victim and survivor transactions, locks held and waited for, and **Show raw output** / **Hide raw output** in the inspector).
  - Controls for **Waits only** (hiding non-waiting transactions and held locks that block nothing) and **Auto-refresh** (**Off**, **Every 2 s**, **Every 5 s**, **Every 10 s**).
- **Actions**: selecting a session or transaction opens the inspector with **Show plan** (when a running query can be explained) and **Kill…**. Choosing **Kill…** opens the `End connection <id>?` review sheet, which shows the target session's user, host, state, open transaction age, modified row count (`trx_rows_modified`), and any XA transaction state, lets you choose **What to end** (**Kill connection** for `KILL <id>` or **Kill query only** for `KILL QUERY <id>`) below **Statement to send**, and re-verifies that the thread still belongs to the same user and start time before sending. On **Production** connections, or when ending a blocker with uncommitted changes, typing the connection ID is required. After sending `KILL`, myflames polls the server to confirm whether the thread exited, is rolling back (`Killed (rolling back)`), or stayed in `XA PREPARED`.
- **Engine and privilege notes**: MySQL 8.0+ reads `performance_schema.data_locks`, `data_lock_waits` and `metadata_locks` alongside `information_schema.innodb_trx`. MySQL 5.7 reads `information_schema.INNODB_LOCKS` and `INNODB_LOCK_WAITS` and notes that metadata locks require `performance_schema.metadata_locks` instrumentation. MariaDB reads `information_schema.INNODB_LOCKS`, `INNODB_LOCK_WAITS` and `INNODB_TRX`, and uses `information_schema.METADATA_LOCK_INFO` when the `metadata_lock_info` plugin is loaded (showing `INSTALL SONAME 'metadata_lock_info'` in the inspector when it is not). Killing another user's session requires `CONNECTION_ADMIN` or `SUPER` on MySQL (`KILL ADMIN` or `SUPER` on MariaDB).

## Indexes

**Server** > **Indexes** inspects index definitions, cardinality, size and runtime usage across your schemas to find unused, redundant and full-scan indexes.

- **What you see**: a summary strip and a paginated table (**Rows** per page: 25, 50, 100 or 200) with segmented **List** filters for **All indexes**, **Unused**, **Redundant** (indexes whose leading columns duplicate another index on the same table), **Full scans** and **No data**, plus a **Databases** picker, **Filter indexes** search, and **Export** (**CSV**, **HTML**, **PDF…**). When the selected schemas exceed 2,000 tables, a scope gate pauses the full read and offers **Read all anyway** or narrowing **Databases** first. Selecting an index opens the inspector with its columns, cardinality, size, read/write counters, any redundant partner index, and a **Changed through myflames** history of recent visibility or drop actions from this computer.
- **Actions**: the inspector action bar and each row's `⋯` and right-click menus offer reviewed index changes (menu items carry trailing ellipses; inspector buttons use the direct labels):
  - **Set invisible** / **Set invisible…** and **Set visible** / **Set visible…** on MySQL 8.0 and later (`ALTER TABLE ... ALTER INDEX ... INVISIBLE` / `VISIBLE`), letting you test whether the optimizer misses an index before dropping it.
  - **Set ignored** / **Set ignored…** and **Set not ignored** / **Set not ignored…** on MariaDB 10.6 and later (`ALTER TABLE ... ALTER INDEX ... IGNORED` / `NOT IGNORED`).
  - **Drop index** / **Drop index…** (and **Drop primary key…** in the row menu when applicable), which requires typing the index name to confirm and warns that dropping an index is not reversible without rebuilding it.
  - **Table health**, which jumps to **Server** > **Tables** focused on that index's table.
- **Engine and privilege notes**: index usage comes from `performance_schema.table_io_waits_summary_by_index_usage` (cumulative since the last server start or table rebuild). On MariaDB or Percona Server when Performance Schema index instrumentation is off and `userstat=ON`, `information_schema.INDEX_STATISTICS` provides read counts. MySQL 5.7 has no invisible indexes (`ALTER INDEX ... INVISIBLE` arrived in MySQL 8.0), so only drop actions apply there. Modifying an index requires `INDEX` and `ALTER` privileges on the table.

## Tables

**Server** > **Tables** checks table sizes, row counts, engines, auto-increment capacity, missing primary keys and InnoDB tablespace fragmentation.

- **What you see**: a summary strip and a paginated table with three **List** views:
  - **All tables**: data size, index size, total size, estimated rows, auto-increment usage, engine, collation and row format, with **Filter tables** and **Export** (**CSV**, **HTML**, **PDF…**).
  - **Missing primary keys**: tables that have no explicit `PRIMARY KEY` and no `NOT NULL UNIQUE` key on InnoDB, with **Status** (**All**, **Problem**, **Watch**) and **Engine** filters. The inspector's **Why a primary key matters** section explains row-based replication stalls (slave applier full table scans) and InnoDB's hidden 6-byte `DB_ROW_ID` cluster key contention.
  - **Fragmentation**: tables where `DATA_FREE` is high relative to total tablespace size, with **Show** (**Candidate tables** or **All fragmented tables**) and **Minimum fragmentation %** controls. The inspector shows the **Rebuild** statements (`OPTIMIZE TABLE` and `ALTER TABLE ... ENGINE=InnoDB`) with **Open in Query editor** and notes on online DDL space requirements and `innodb_file_per_table`.
- **Controls**: **Databases** selects which schemas to inspect (defaulting to the connection's default database when set). On MySQL 8.0 and later, checking **Fresh numbers** sets `information_schema_stats_expiry=0` for the read session so `information_schema.TABLES` returns current storage-engine numbers instead of cached 24-hour values. Above 2,000 tables, **Read all anyway** confirms reading every schema.
- **Actions**: selecting a table or opening its row `⋯` or right-click menu offers:
  - **Table structure**, which opens a read-only dialog with **Columns**, **Indexes**, **Foreign keys** and **CREATE TABLE** tabs plus **Copy CREATE TABLE** and **Download .sql**.
  - **Optimize `<table>`** / **Optimize table…**, **Analyze `<table>`** / **Analyze table…**, and **Check `<table>`** / **Check table…** (plus **Checksum table…**, **Truncate table…** and **Drop table…** in the right-click menu), each reviewed before execution with its locking and replication notes.
  - **Add column** / **Add column…** and **Remove column** / **Remove column…**, which build and review an `ALTER TABLE` statement (with algorithm and lock clauses where supported).
  - **Import CSV…**, which opens the CSV importer pre-filled for that table (see [Query editor & slow queries](queries.md#import-csv)).
  - **Indexes** / **View indexes** (to jump to **Server** > **Indexes** filtered to that table), **Open in Query editor**, and **Show CREATE TABLE (DDL)**.
- **Engine and privilege notes**: reads `information_schema.TABLES`, `STATISTICS` and `COLUMNS`. Table maintenance and schema changes require `ALTER`, `INSERT`, `SELECT` or `DROP` privileges on the target table depending on the operation.

## Parameters

**Server** > **Parameters** inspects every server system variable, stages and reviews runtime and persisted configuration changes, compares parameters across two servers or snapshots, and tracks parameter changes across MySQL and MariaDB releases.

### Parameters

- **What you see**: every variable from `SHOW GLOBAL VARIABLES` paired with its default, variable source (`performance_schema.variables_info` on MySQL 8.0+: compiled default, option file path, `SET GLOBAL`, `SET PERSIST`, command line), dynamic vs static mutability, and tuning recommendations.
- **Controls**: **Filter parameters** searches by variable name, value or description, and **Show** filters by **All**, **Modified** (variables that differ from their engine default or come from an explicit configuration source), **Dynamic**, **Static**, **Recommendations** (variables flagged with a tuning rule), and **Pending** (while staging edits).
- **Actions**:
  - Single-parameter changes in the inspector: **Change this parameter…** opens a review sheet where you choose how the change applies: **Now only** (`SET GLOBAL`), **Now and after restart** (`SET PERSIST` on MySQL 8.0+), **After restart only** (`SET PERSIST_ONLY` on MySQL 8.0+ for static variables too), **Session** (**Open in Query editor** with `SET SESSION`), or **Remove the persisted value** / **Reset persisted value…** (`RESET PERSIST IF EXISTS <name>`). The inspector also offers **Reset to default**, **Version history** (jumping to the **Versions** tab for that variable), **Documentation** (opening the official MySQL, Percona Server or MariaDB manual entry), and a **Changed through myflames** history with **Undo…** to revert a prior change.
  - Batch editing: click **Edit** in the toolbar to reveal inline value controls across dynamic parameters (or use **Stage value for review** in the inspector). Staging changes reveals a batch bar with **Preview changes (`<N>`)** and **Review and apply (`<N>`)** (up to 25 parameters at once, with a **Keep after restart** checkbox on MySQL 8.0+ that switches between `SET PERSIST` and `SET GLOBAL`). Every staged change is reviewed and audited as one batch.
- **Engine and privilege notes**: `SET PERSIST`, `SET PERSIST_ONLY`, `RESET PERSIST` and `performance_schema.variables_info` require MySQL 8.0 or later (with `SYSTEM_VARIABLES_ADMIN` or `SUPER`, plus `PERSIST_RO_VARIABLES_ADMIN` for `SET PERSIST_ONLY`). On MariaDB and MySQL 5.7, runtime changes use `SET GLOBAL` (requiring `SUPER` or `SYSTEM_VARIABLES_ADMIN` on MariaDB 10.5.2+) and the review sheet includes the `[mysqld]` option-file line to copy so the setting survives a restart.

### Compare

Switch to the **Compare** tab at the top of **Server** > **Parameters** to compare system variables between any two saved connections or saved parameter snapshots.

- **Controls**: pick **Source** and **Target** (each lists your saved connections and any snapshots saved on this computer), use **Swap source and target** to flip the direction, and click **Compare**. **Save snapshot…** in the top bar saves the current server's parameters locally so you can compare before and after a maintenance window, **Manage snapshots (`<N>`)** renames or deletes saved snapshots, and **Refresh choices** reloads the picker lists.
- **Filtering**: by default, identical variables and host-specific identifiers (`hostname`, `server_uuid`, `port`, socket and directory paths) are hidden so you see only meaningful configuration drift. Use **Filter differences** to search by variable name or value, check **Show identical** to include matching rows, and check **Show server-specific settings** to include instance-identity variables.

### Versions

Switch to the **Versions** tab at the top of **Server** > **Parameters** to browse the built-in MySQL and MariaDB parameter version catalogs offline.

- **Compare versions**: choose **Engine** (**MySQL** or **MariaDB**), pick **From** and **To** release versions (or click **Swap**), filter by **Show changes** (**All changes**, **Added**, **Removed**, **Deprecated**, **Default changed**) or **Filter parameters**, and check **Only parameters set on `<server>`** when connected to focus on variables modified on the active server.
- **Parameter history**: switch the segmented control to **Parameter history** and pick a variable in **Parameter** (or click **Show full history** in the inspector) to trace when it was introduced, when its default changed, when it was deprecated, and when it was removed across releases.

## Instruments

**Server** > **Instruments** manages Performance Schema setup tables (`setup_instruments`, `setup_consumers`, `setup_actors` and `setup_objects`) so you can turn on the exact instrumentation a diagnostic view needs and restore the previous setup when finished.

- **What you see**: a summary strip (Performance Schema state, enabled instruments and consumers, and memory used by Performance Schema) and four tabs:
  - **Features**: high-level capability rows (such as statement digests, stage progress, metadata locks, data locks, memory summary, table and file I/O, and replication receiver detection) showing which views depend on each feature and whether its required instruments and consumers are active.
  - **Instruments**: `performance_schema.setup_instruments` with **Search instruments**, **Instrument group** (**All groups**, `wait`, `stage`, `statement`, `transaction`, `memory`, `idle`, `error`, `metadata`) and **Instrument state** (**All states**, **Enabled**, **Timed**, **Disabled**).
  - **Consumers**: `performance_schema.setup_consumers` showing which event history and summary tables collect events, and whether each consumer is effective given its parent consumers.
  - **Actors and objects**: `setup_actors` and `setup_objects` rules controlling which foreground users/hosts and which schemas/objects are instrumented.
- **Actions**:
  - Presets in the toolbar: pick a **Preset** (such as statement diagnostics, lock investigation, memory profiling, or minimal overhead), click **Show statements** to preview the SQL, and in the inspector choose **Apply `<preset>`**. Applying a preset snapshots the rows it touches first so you can click **Restore setup for `<preset>`** or **Undo `<preset>`** to put the server's prior state back.
  - Batch changes: select rows in **Instruments** or **Consumers** (using **Select all shown** or **Clear selection**) and choose **Enable**, **Enable without timing** (instruments), or **Disable**. On MySQL 8.0+, check **Keep after restart** when persisting instrument state is supported; the **How changes apply** popover explains what takes effect immediately versus for new sessions or objects.
  - In **Actors and objects**, add or delete filter rows, or choose **Restore `setup_actors` defaults** and **Restore `setup_objects` defaults**.
- **Engine and privilege notes**: requires `SELECT` and `UPDATE` on `performance_schema.setup_*` tables (plus `INSERT` and `DELETE` on `setup_actors` and `setup_objects`). If `performance_schema=OFF` at startup, the view explains that enabling it requires `performance_schema=ON` in the server option file and a restart.

## Maintenance

**Server** > **Maintenance** runs pre-upgrade checks, logical dumps, restores and physical clones through local client tools (`mysqlsh`, `mysqldump`, `mariadb-dump` and `mysql` / `mariadb`).

### Tools

- **What you see**: Maintenance finds the MySQL and MariaDB tools on this computer as soon as it opens. **Used for this server** names the program, version, origin and selection reason for queries, dumps, restores and MySQL Shell when selected (with warnings for missing or older tools, and **Change…** to open **Client tools**), **Detected tools** lists every copy found on this computer with its path and origin, and **Offered for this server** shows which maintenance operations those tools support. **Client tools** (also available from **Settings** > **Client tools** > **Client tools…**) lets you keep **Automatic (best match for each server)** or choose an installation separately for MySQL and MariaDB servers; SQL restores and `CLONE` use the client from the selected dump installation, and a missing program in a chosen installation is reported without substituting another installation. Click **Check for updates** to check vendor tool updates on request, click **Detect again** after installing or updating MySQL Shell or database client packages, or use **Get MySQL Shell** in **Client tools** (see [Get MySQL Shell](howto-server.md#get-mysql-shell)).
- **MySQL Shell on demand**: when no usable MySQL Shell is on this computer, the **MySQL Shell** section of **Client tools** offers **Get MySQL Shell** (or **Get MySQL Shell 9.7.0** when an installed copy is older than 9.7.0, and **Open Oracle downloads** on an unsupported platform). It downloads Oracle's pinned MySQL Shell 9.7.0 build into myflames's data folder (`tools/mysqlsh`) with its SHA-256 checksum verified before anything runs, shows the progress with a **Stop** button (and **Try again** if an attempt fails), and links **GPLv2 license (Oracle)** and **Oracle downloads**; myflames does not redistribute MySQL Shell. **Cluster**, the **Maintenance** tools and the client chooser then use it.

### Upgrade check

- **What you see**: runs MySQL Shell's `util.checkForServerUpgrade()` against a MySQL server (use **Get MySQL Shell** in **Settings** > **Client tools** > **Client tools…** when MySQL Shell is not installed yet), or a native SQL check subset when MySQL Shell is not installed or when **Partial check without MySQL Shell (native subset)** is checked.
- **Controls and actions**: **Target version** comes from the vendor (MySQL Community versions from the official release notes, Percona Server versions from Percona's package repositories; offline, MySQL targets come from the releases bundled with myflames), offering only releases on a supported upgrade path (patches of your series, the next LTS series, and Innovation releases before it, excluding releases Oracle removed from download or published only as a Docker image), newest first with the newest release of the next LTS chosen by default. Below the list, myflames says how the server was installed (RPM packages, DEB packages, Ubuntu's own package or a generic archive, with the evidence under **How this was decided**) and what that means: which repository publishes the target, or for Percona the `percona-release enable-only` command for the target's repository. Choose a **Target version** (or **Other version…** to enter a specific `8.x` or `9.x` release), click **Check upgrade**, inspect the resulting errors, warnings and notices in the table and inspector, or choose **Export JSON** to save the report. On MariaDB, the tab explains that pre-upgrade checks use `mariadb-upgrade --check-only` after installing the new binaries.

### Dump

- **What you see and configure**: choose **Scope** (**Whole instance** or **Databases**), select **Databases** and optional **Tables**, pick **Tool** (the list offers only tools that can run, and **Automatic** prefers MySQL Shell `util.dumpInstance` / `util.dumpSchemas` / `util.dumpTables` on MySQL and names `mysqldump` or `mariadb-dump` when no MySQL Shell is installed; **SQL dump** chooses the SQL tool directly), choose an **Output folder** (defaulting to a timestamped subfolder under `~/.myflames/dumps`), and set **Options** including **Structure only (no rows)** (`--no-data` / `ddlOnly: true`), routines, events, triggers, single-transaction snapshot, and parallelism threads. When no client tool can run a dump for the server (for example, a MariaDB server on a computer without MariaDB client tools), the tab names the missing program with **Choose client tools…** instead of starting.
- **Actions**: click **Start dump…** to check first (reading only), review the exact command line (with password arguments redacted) and confirm. A running job shows a progress bar, the step it is on and the elapsed time (MySQL Shell reports its own percent; `mysqldump` and `mariadb-dump` print nothing, so for them the bar shows an estimate such as `≈46%` from bytes written to `dump.sql` against the server's table sizes while that estimate exists and output stays below it, otherwise keeping the bar moving without a percent), along with bytes written and rate on the job card and a compact summary beside **Start dump…** with **Show progress** to jump to the job card. On macOS, a dump you started opens its folder in Finder when it completes, and **Open in Finder** opens it again; on Windows, use **Open in File Explorer**. Choose **Export manifest** to save the dump metadata JSON.

### Restore

- **What you see and configure**: select a **Dump folder** containing a MySQL Shell dump or `.sql` dump created on this computer, then configure **Options**:
  - **Default database**: **As in the dump**, an existing database from the pick list, or **New database…** to create and target a new schema when restoring a single-database SQL dump.
  - **Existing objects**: **Stop if any exist** (default, refusing the restore if target tables already exist), **Skip existing (MySQL Shell only)**, or **Drop and recreate** (for SQL dumps that include `DROP TABLE IF EXISTS`).
  - Safety and resume switches: **Allow restoring into the server the dump came from** (required when the target server's `server_uuid` matches the dump's source server), **Resume an interrupted MySQL Shell load**, and **Threads**.
- **Actions**: when no client tool can run a restore for the server, the tab names the missing program with **Choose client tools…** instead of starting. Otherwise click **Start restore…** to check first (reading only), review the exact commands and target server policy, type the confirmation guard when required (such as on **Production** or when **Drop and recreate** is chosen), and run the restore with live progress, step, elapsed time and a cancel button.

### Clone

- **What you see and configure**: copies a MySQL 8.0.17+ or Percona Server instance from a remote donor (`CLONE INSTANCE FROM ...`) or into a local directory. Pick **Fill from saved connection** (which lists direct saved connections and excludes SSH-tunnel connections because the recipient server connects to the donor directly over the network), or enter **Donor host**, **Donor port**, **Donor user**, **Donor password**, and **Donor address as the recipient reaches it** when the recipient reaches the donor under a different hostname or IP. Choose **Mode** (**Replace the recipient's data**, which wipes the recipient's data directory and restarts it, or **Into a new data directory**) and **Donor TLS** (`SSL` or `NO SSL`).
- **Actions**: click **Start clone…** to review the exact `CLONE INSTANCE` statement and prerequisite checks (matching exact server version, `clone` plugin installed, `BACKUP_ADMIN` on the donor, `CLONE_ADMIN` on the recipient), type the recipient confirmation guard when replacing data, and monitor stage progress through `performance_schema.clone_status` and `clone_progress`. MariaDB does not have `CLONE INSTANCE`; the tab points to `mariadb-backup` instead.

## Users and roles

**Server** > **Users and roles** inspects database accounts, roles, authentication plugins, password state, TLS requirements, resource limits and privilege grants, and edits them with staged SQL review.

- **What you see**: a summary strip (total users, roles, locked accounts, accounts without a password, wildcard-host accounts, and superuser accounts) and a table of accounts and roles with **Find an account** search. Selecting an account opens the inspector with three tabs:
  - **Grants**: choose **Grant level** (**Global**, **Databases**, **Tables**, **Columns**, **Routines** or **Proxy**) and **Grant scope** (or click **Add scope** and **Use scope** to grant on a new `db.*` or `db.table` target), toggle individual privileges or **Grant option for static privileges on `<scope>`**, and inspect effective privileges.
  - **Account**: authentication plugin, password status, account lock state, TLS requirement (`NONE`, `SSL`, `X509`), and per-hour/connection resource limits (`MAX_QUERIES_PER_HOUR`, `MAX_UPDATES_PER_HOUR`, `MAX_CONNECTIONS_PER_HOUR`, `MAX_USER_CONNECTIONS`).
  - **Roles**: roles granted to the user (or grantees of a role), with checkboxes for granted membership, **Admin option** (`WITH ADMIN OPTION`), and **Default** (`SET DEFAULT ROLE`).
- **Actions**:
  - Toolbar: **New user** and **New role** open creation sheets (with **Generate password** for users) that stage and review `CREATE USER` or `CREATE ROLE`.
  - Inspector buttons: **Lock** / **Unlock**, **Expire password**, **Set password**, **Rename**, and **Drop user** / **Drop role**.
  - Staging bar: toggling checkboxes in **Grants** or **Roles** stages the resulting `GRANT`, `REVOKE` and `SET DEFAULT ROLE` statements under **Pending changes** with **Review changes (`<N>`)** and **Discard**. The inspector also lists **Changed through myflames** so you can review or undo recent account changes made from this computer.
- **Compare**: switch to the **Compare** tab at the top of **Users and roles** to diff accounts, authentication settings, roles and grants between **Source** and **Target** connections. Choose **Export grants as SQL** (selecting **From**: **Source** or **Target**, or **All accounts only in source**, then **Export grants as SQL (`<N>`)**) to generate `CREATE USER`, `CREATE ROLE`, `GRANT` and `SET DEFAULT ROLE` statements that you can **Copy** or **Download .sql** (`ALTER USER` password hashes are omitted so secrets are never exported).
- **Engine and privilege notes**: MySQL 5.7 has no roles (`CREATE ROLE` arrived in MySQL 8.0), so **New role** and the **Roles** tab are hidden on 5.7 and the view notes why. MariaDB roles use `CREATE ROLE`, `GRANT <role> TO <user>` and `SET DEFAULT ROLE` without host parts on role names. Reading account metadata uses `mysql.user`, `mysql.role_edges`, `mysql.default_roles` (or `information_schema.APPLICABLE_ROLES` on MariaDB) and `SHOW GRANTS`; modifying accounts requires `CREATE USER`, `GRANT OPTION` or `ROLE_ADMIN` depending on the statement.

## Top statements

**Workload** > **Top statements** ranks normalized SQL digests from `performance_schema.events_statements_summary_by_digest` so you can find the queries consuming the most server time, rows examined or unindexed scans.

- **What you see**: a summary strip (including digest table fill level and overflow warnings when `events_statements_summary_by_digest` is full) and a ranked table of statement digests showing call count, total time, average time, p95 or max latency, rows examined, rows sent, temporary tables on disk, full scans and joins without an index.
- **Controls**: **Rank by** sorts and queries the server by **Total time**, **Average time**, **Rows examined**, **Calls**, **Joins without an index**, **Full scans of the first table**, or **Reads without an index**. Filter by **Schema** or **Filter statements**, and choose **Top N** (**10**, **25**, **50** or **100**).
- **Actions**:
  - **Explain top `<N>`** in the toolbar runs estimated `EXPLAIN FORMAT=JSON` plans for the top eligible `SELECT` digests in the list (after a confirmation sheet when needed) and flags the worst findings inline.
  - Selecting a statement opens the shared statement inspector with **Open in Query editor**, **Explain** (captures an estimated plan and opens it in **Plans**), **Run analysis** (opens a confirmation dialog where **Execute and analyze** runs `EXPLAIN ANALYZE FORMAT=JSON` on MySQL 8.3+ or `ANALYZE FORMAT=JSON` on MariaDB for `SELECT` statements), and **Suggested index** > **Read suggestion** when the digest is flagged for full scans or missing index usage (see [Query editor & slow queries](queries.md#find-slow-queries)).
- **Engine and privilege notes**: requires `SELECT` on `performance_schema.events_statements_summary_by_digest` with the `statement_digest` consumer enabled. MySQL 5.7 has no `QUERY_SAMPLE_TEXT`, percentile columns or CPU time in `events_statements_summary_by_digest`, so the view shows the normalized digest text and notes what 5.7 omits.

## Processlist

**Workload** > **Processlist** shows live client sessions, running queries, stage progress, memory usage and transaction state, with single-session and bulk termination.

- **What you see**: a summary strip (total sessions, active threads, sleeping threads, locked sessions, longest running query and open transactions) and a live session table (`ID`, `User`, `Host`, `Database`, `Command`, `Time`, `State`, `Progress`, `Memory`, `Trx age`, `SQL`). Selecting a session opens the inspector with its full SQL text, connection attributes, transaction details, **DDL progress** (from `performance_schema.events_stages_current` when stage instruments are enabled), and **Recent statements** from `events_statements_history`.
- **Controls**: filter by state (**Active**, **All**, **Locked**), **Running at least** duration, or **Filter sessions** search; pick **Source** (**Auto (P_S / I_S)**, which joins `performance_schema.threads`, `information_schema.innodb_trx` and session memory, or **SHOW PROCESSLIST**); toggle **Follow progress** to poll stage progress for long-running operations; and set **Auto-refresh** (**Off**, **Every 2 s**, **Every 5 s**, **Every 10 s**).
- **Actions**:
  - Single session: choose **Show plan** or **Kill** in the inspector, **Show plan** or **Kill…** in the row `⋯` menu, or **Kill query…** / **Kill connection…** in the right-click context menu. Each kill opens the `End connection <id>?` review sheet with transaction rollback warnings (`trx_rows_modified`), XA prepared-transaction checks, and post-kill verification.
  - Bulk kill: click **Kill sessions…** in the toolbar to open the mass-kill review dialog. Choose **Kill query** (`KILL QUERY`) or **Kill connection** (`KILL`), start from one of the **Presets** (**Runaway queries (> 30s)**, **Idle sleeping (> 60s)**, **Lock waiters**, **All clients**) or set filters for **Time condition**, **Match user**, **Ignore users**, **Command**, **Database**, **Match host**, **Match query pattern (regex or text)** and **Lock waits only**. Your own session, system threads (`system user`, `event_scheduler`) and active replication dump threads are excluded automatically. The dialog previews every matching session, warns about uncommitted InnoDB changes, requires typing the confirmation phrase on **Production** or when killing connections, re-verifies each thread's identity before sending, and reports per-session outcomes in the **Audit** log.

## Memory

**Workload** > **Memory** shows how much memory the server has allocated across global buffers and per-session threads using Performance Schema memory summary tables.

- **What you see**: a summary strip (total tracked memory, global vs thread memory, high-water marks, and buffer pool size) and a breakdown table switched between **By category** (grouped by subsystem such as `innodb`, `sql`, `temptable`, `performance_schema`), **By session** (memory allocated per connected thread, linked to the session's user and current query), and **By account** (`user@host` totals), plus **Top memory events** listing individual `memory/*` instruments.
- **Controls**: **Window** samples memory growth over an interval, and **Refresh** takes a fresh snapshot.
- **Actions**: read-only. When memory instrumentation is disabled, the view links to **Server** > **Instruments** to enable `memory/%` instruments.
- **Engine and privilege notes**: MySQL 5.7+ and Percona Server read `performance_schema.memory_summary_global_by_event_name`, `memory_summary_by_thread_by_event_name` and `memory_summary_by_account_by_event_name` (MySQL 8.0 enables memory instruments by default; MySQL 5.7 requires enabling `memory/%` in `setup_instruments`). MariaDB does not populate Performance Schema memory summary tables in the same way; when unavailable, the view reports what the engine exposes through status variables and `information_schema.INNODB_BUFFER_POOL_STATS`.

## Waits

**Workload** > **Waits** samples `performance_schema.events_waits_summary_global_by_event_name` to show where server threads spend time waiting on I/O, locks, mutexes, rw-locks and condition variables.

- **What you see**: a summary strip and a ranked table of wait events or wait classes (`wait/io/file`, `wait/io/table`, `wait/synch/mutex`, `wait/synch/rwlock`, `wait/synch/cond`, `wait/lock/table`, `wait/io/socket`), showing event count, total wait time, average wait, maximum wait and percentage of total wait time, plus a **Not instrumented** disclosure listing wait categories that are currently disabled or untimed.
- **Controls**: choose **Window** (**1 s**, **2 s**, **5 s**, **10 s**), switch between **Over the window** (delta between two snapshots) and **Since server start** (cumulative totals), switch between **Events** and **Classes**, and set **Auto-refresh**.
- **Actions**: read-only. If wait instruments or timing are off, the view links to **Server** > **Instruments** so you can enable and time the relevant `wait/%` instruments.
- **Engine and privilege notes**: requires `performance_schema=ON` and `SELECT` on `performance_schema.events_waits_summary_global_by_event_name`. Idle waits (`wait/idle`) are separated so background idle time never hides active contention.

## I/O

**Workload** > **I/O** measures table-level row I/O and file-level disk I/O latency and volume.

- **What you see**: **Server-wide InnoDB I/O** summary tiles (reads, writes, fsyncs and bytes per second from InnoDB status counters) and three breakdown tabs:
  - **Tables**: row read, insert, update and delete counts and wait times per table from `performance_schema.table_io_waits_summary_by_table` (or `information_schema.TABLE_STATISTICS` when `userstat=ON` on MariaDB and Percona Server).
  - **Files**: physical file reads, writes, fsyncs, byte volumes and latencies from `performance_schema.file_summary_by_instance`.
  - **File kinds**: file I/O aggregated by Performance Schema file event type (`innodb_data_file`, `innodb_log_file`, `binlog`, `relaylog`, `temp`, `slow_log` and others) from `performance_schema.file_summary_by_event_name`.
- **Controls**: filter by **Schema**, choose **Window** (**1 s**, **2 s**, **5 s**, **10 s**), and switch between **Over the window** and **Since server start**.
- **Actions**: read-only.

## Tuning

**Tuning** combines the **Scorecard** and **Full analysis** in one place (`Tuning` in the sidebar, with a **Scorecard** | **Full analysis** segmented tab control in the header).

- **Scorecard**:
  - **What you see**: an overall percentage score and letter grade (`Grade A` through `Grade F`, or `Provisional` until at least half of the applicable checks and at least one check in every category are measured; any **Problem** caps the grade at `C`, explained in the **How the grade works** popover) across five weighted categories: **Buffer pool and redo** (30%), **Queries** (25%), **Connections and threads** (20%), **Tables and caches** (15%), and **Security** (10%).
  - **Controls**: click a category card to filter to it, use **Show** (**Needs attention**, **Not measured**, **All checks**) and **Search checks**, or choose **Export the tuning scorecard** (**HTML**, **Markdown**, **JSON**).
  - **Measuring and acting**: the scorecard reuses reports already read for the connection in use (**Health**, **Parameters**, **Tables** and **Full analysis**). An unmeasured check shows what would measure it and offers **Open Health**, **Open Parameters**, **Open Tables** or **Run full analysis** in the inspector. Suggested SQL (`SET PERSIST` on MySQL 8.0+, `SET GLOBAL` plus an option-file line on MariaDB and MySQL 5.7, or `SET SESSION` for per-session buffers) can be copied or opened with **Open in Query editor**; nothing on the **Tuning** page executes changes directly.
- **Full analysis**:
  - **What you see**: clicking **Run full analysis** runs every **Server** diagnostic check once in a single read-only pass (about 10 to 20 s, because **Health**, **Waits** and **I/O** sample a 10 s window) and presents a summary line, server facts strip (`Server`, `Host`, `Uptime`, `Taken`, `Databases`, `Views read`), **Look at first** (the single highest-priority finding), **To look at** (all remaining **Problem** and **Watch** findings ranked by severity), **Not judged** (checks or views that could not run due to missing privileges or disabled Performance Schema, which never count as OK), **Sections** (each diagnostic area's summary), and **For information, no rule applies**.
  - **Inspector and export**: selecting a finding shows its **Verdict**, **Numbers**, **Settings** (current value and default), **Rule**, **Why it matters**, **What to do** (statements and `my.cnf` lines to copy), **Statements behind it** / **Statements that name each table** when Performance Schema digests are available, and buttons to jump to the matching **Server** view or **Learn** lesson. **Export the full analysis** saves the report as **HTML**, **Markdown**, **JSON** or **Text**.

## Connection groups

When you open **Replication**, **Cluster**, **ProxySQL** or **Readyset**, myflames can cross-check related servers in your topology (for example, verifying a replication source's version, linking a ProxySQL backend to its cluster node, or matching a Readyset upstream to a saved MySQL connection).

- **Consent rule**: myflames logs in with saved credentials only to other saved connections that share the same **Group** name as the connection in use, and never to a connection outside that group. If the connection in use is unsaved or has no **Group**, myflames reads only the connection you opened.
- **Assigning a group**: set the optional **Group** field (up to 80 characters) when creating or editing a connection on **Home**, or use the connection group bar at the top of the **Topology** tab in **Replication**, **Cluster**, **ProxySQL** or **Readyset**.
- **What the group bar shows**:
  - When the connection in use is not saved: `Save this connection to add it to a group.`
  - When the connection belongs to a group: `Group <name>` followed by which group members were read (`read <names>`) and whether any member failed or was not reached (`<name> failed` or `not reached`).
  - When the open server's topology matches an existing group `<G>` (from server identities remembered only from connections you have opened on this computer, or from peer addresses the open server reports): `This connection is part of the topology of group <G> (<evidence>). Add it to <G>?` with **Add to `<G>`** and **Not now**.
  - When other saved connections on this computer match the open server's topology: `<N> saved connection(s) is/are part of this topology` with **Review…**, which opens the **Review topology connections** (or `Add connections to <group>`) sheet where you can check the matching connections, set or confirm the **Group** name, and click **Add `<N>` to `<group>`**.
  - When the connection is saved without a group and no automatic match is waiting: `No connection group: myflames reads only this connection.` with **Create a group…**, which opens **Create a connection group** to name a group and optionally include other saved connections.

To create a group, inspect a whole group in **Topology** and roll a parameter change across its members, see [Create a connection group from Home](howto-topology.md#create-a-connection-group-from-home), [Read a whole group in Topology](howto-topology.md#read-a-whole-group-in-topology) and [Change a parameter on every server](howto-topology.md#change-a-parameter-on-every-server).

For connection setup details, see [Connection policies & write safety](safety.md#connection-groups-and-topology-consent) and the [Connections and files how-to guides](howto-connections.md).

## Replication

**Replication** inspects asynchronous and semi-synchronous replication channels (MySQL and Percona Server) or connections (MariaDB) on the connection in use and offers reviewed transaction-skip recovery when an applier stops on an error.

- **What you see**: a summary line, metric tiles (**Replica state**, **Channels** or **Connections**, **Max applier lag**, **GTID mode**), the connection group bar, and five sub-tabs:
  - **Topology**: a diagram of each replication source and this replica on a lit stage with server cards floating above it (with links to switch to a saved connection in the same group or open **Cluster**, **ProxySQL** or **Readyset** when linked); motion marks channels that were running when last read, turns off with your system's reduced-motion setting, and is explained in the place's `ⓘ`. If the server is not a replica, an empty state explains why and offers **Open Cluster** or **Open Readyset** when applicable.
  - **Channels** (MySQL) / **Connections** (MariaDB): each channel's **Status**, **Source** (`host:port`), **I/O** thread state, **SQL** thread state, **Lag** and **Error**. Group Replication channels (`group_replication_applier`, `group_replication_recovery`) are listed as `Not judged` here because **Cluster** judges them.
  - **Lag**: **Lag**, **Configured delay** (`SQL_Delay`), **Remaining delay**, **Worker signals** (parallel applier worker states and Coordinator waits) and **Lag caveats** (why `Seconds_Behind_Source` / `Seconds_Behind_Master` alone does not prove a replica is caught up).
  - **GTID**: a server-wide GTID fact strip (**GTID mode**, **Enforce GTID consistency**, **GTID slave position**, **GTID current position**, **GTID domain ID**, **GTID strict mode**) and per-channel **Failing GTID**, **Read position**, **Executed position** and (on MySQL) **Assign GTIDs** (`ASSIGN_GTIDS_TO_ANONYMOUS_TRANSACTIONS`).
  - **Recovery**: each channel's **Last error**, **Skip plan** (`Empty GTID` or `Skip counter`), and a **Skip…** button when a safe skip plan is available.
- **Actions**: selecting a stopped or errored channel opens the inspector with **Skip this transaction…** and **Skip until stopped…** (also reachable via **Skip…** in the **Recovery** tab).
  - **Skip this transaction…** re-reads the failure, opens a review sheet showing the failing GTID or binary log coordinates, the SQL error number and table, the data-drift warning, and the **Exact skip statements** (injecting an empty transaction with `SET GTID_NEXT='<gtid>'; BEGIN; COMMIT; SET GTID_NEXT='AUTOMATIC'` when GTIDs are in use on MySQL, or advancing `sql_slave_skip_counter` / `gtid_slave_pos` when appropriate), then clicks **Skip transaction** and verifies that the applier moved past that transaction.
  - **Skip until stopped…** opens a review sheet where you check which error codes to skip under **Skip only these errors** (such as `1062 Duplicate key`, `1032 Row not found`, `1452 Foreign key child row`, or the current error code) and set **Stop after this many skips** (1 to 1,000, default 10) and **Stop after this many minutes** (1 to 1,440, default 10), then click **Start skipping**. Each subsequent failure is planned, verified, skipped and audited individually; the loop stops automatically on any other error code, when a receiver reconnects (when receiver detection is active; if off, the sheet links to **Server** > **Instruments**), when either limit is reached, when myflames quits, or immediately when you click **Stop** in the loop banner.
- **Engine and privilege notes**: reads `SHOW REPLICA STATUS` (or `SHOW SLAVE STATUS` on older MySQL and `SHOW ALL SLAVES STATUS` on MariaDB) and `performance_schema.replication_*` tables (`REPLICATION CLIENT` or `REPLICA MONITOR` privilege). Skipping a transaction requires `REPLICATION_SLAVE_ADMIN` or `SUPER` (plus `SYSTEM_VARIABLES_ADMIN` or `SUPER` for `GTID_NEXT` / `sql_slave_skip_counter`, and `REPLICATION_APPLIER` on MySQL 8.0+ for tagged GTIDs).

See the [Replication, clusters and proxies how-to guides](howto-topology.md) for walkthroughs.

## Cluster

**Cluster** inspects high-availability clusters on the connection in use: **MySQL InnoDB Cluster** (and **InnoDB ClusterSet**), **MySQL Group Replication**, **MariaDB Galera Cluster**, **Galera Cluster for MySQL**, and **Percona XtraDB Cluster (PXC)**.

- **What you see**:
  - A summary line naming the cluster kind, cluster name, quorum or component state, member counts, and the connected member's state, followed by expandable **Findings** (**Problem** and **Watch** items with **Details** / **Hide details**) and summary tiles (**Quorum** or **Component** with failures tolerated, **Members** or **Nodes**, **This member** / **This node** / **This server**, and **Mode** or **Flow control paused**).
  - Three sub-tabs: **Topology** (the connection group bar and an interactive cluster diagram on a lit stage where server cards float above the floor, the group's line lights up only when every member is healthy, motion follows your system's reduced-motion setting as explained in the place's `ⓘ`, and primary, secondary, read-replica, arbiter/garbd and router nodes appear alongside linked ProxySQL or Readyset tiers), **Members** (or **Nodes** on Galera and PXC: state, role, address, version, certification and applier queues, conflicts, flow control paused, cert failures, and on PXC the gmcast **Segment**), and on InnoDB Cluster **Routers** (registered MySQL Router instances from `mysql_innodb_cluster_metadata` with **Host**, **Version**, **RW port**, **RO port**, **RW split port** and **Last check-in**).
- **Engine differences**:
  - **Group Replication and InnoDB Cluster**: reads `performance_schema.replication_group_members` and `replication_group_member_stats` (plus `mysql_innodb_cluster_metadata` views when InnoDB Cluster is present, including read replicas replicating over `read_replica_replication` and ClusterSet primary/replica cluster membership). On MySQL 5.7, `replication_group_members` has no `MEMBER_ROLE` or `MEMBER_VERSION` column, so roles are derived from `group_replication_primary_member` and remote member versions are marked unknown.
  - **MariaDB Galera and Galera for MySQL**: reads `wsrep_%` status and system variables and `mysql.wsrep_cluster_members`. Standard Galera exposes `wsrep_local_state_comment` and queue metrics only for the connected node, so other nodes in the component are listed without a state verdict until you connect to them (or group their saved connections).
  - **Percona XtraDB Cluster (PXC)**: also reads `performance_schema.pxc_cluster_view`, which exposes every node's `STATUS` (`SYNCED`, `DONOR`, `JOINER`, `PRIMARY`), `LOCAL_INDEX` and `SEGMENT` from a single node.
- **Actions**: selecting a member or node opens the inspector with the reviewed changes valid for that server and state:
  - **Group Replication and InnoDB Cluster**: **Make primary…** (`SELECT group_replication_set_as_primary('<uuid>')` on a secondary, or `dba.getCluster().setPrimaryInstance(...)` via MySQL Shell in a ClusterSet replica cluster), **Stop Group Replication…** (`STOP GROUP_REPLICATION`), **Start Group Replication…** (`START GROUP_REPLICATION`, offered only when `group_replication_bootstrap_group` is verified `OFF`), and **Switch the group to multi-primary…** / **Switch the group to single-primary…** (or **Switch the cluster to multi-primary…** / **Switch the cluster to single-primary…** via MySQL Shell on an InnoDB Cluster).
  - **InnoDB Cluster and ClusterSet with MySQL Shell**: when `mysqlsh` is installed on this computer (or downloaded with **Get MySQL Shell** in **Settings** > **Client tools** > **Client tools…**) and the connection does not use an SSH tunnel (MySQL Shell 8.0.32 or later for AdminAPI actions), the member inspector offers **Rejoin to the cluster…** (`dba.getCluster().rejoinInstance(..., {recoveryMethod: "incremental"})`, requiring MySQL Shell 8.1.0 or later and InnoDB Cluster metadata 2.0.0 or later on a `MISSING`, `OFFLINE` or `ERROR` member, and staying disabled unless the cluster's ClusterSet status is verified as `OK`) and, on the overview for an InnoDB ClusterSet, **Make `<cluster>` the primary cluster…** (`setPrimaryCluster`), **Fail over to this cluster…** (`forcePrimaryCluster`), and **Rejoin `<cluster>` to the ClusterSet…** (`rejoinCluster`).
  - **MariaDB Galera**: on the connected node (or on another node in a **Group connection** for desync and resync), **Desync this node…** (`SET GLOBAL wsrep_desync = ON`), **Resync this node…** (`SET GLOBAL wsrep_desync = OFF`), and when the node is connected in a `non-Primary` component and not joining, **Bootstrap a Primary component…** (`SET GLOBAL wsrep_provider_options = 'pc.bootstrap=YES'`, which requires typing the node name and comparing `wsrep_last_committed` across nodes first).
  - **In a Group connection**: **Rejoin to the cluster…** runs through the active `ONLINE` member with quorum and names the missing instance in the review. Other member changes use that member's saved connection in the group (offering **Edit group…** when no usable saved connection exists). For a remote Galera node, **Desync this node…** and **Resync this node…** stay available for review; the review checks that node's own state on its own connection before allowing either change.
- **Privileges**: reading requires `SELECT` on `performance_schema.replication_group_*` (and `mysql_innodb_cluster_metadata` for InnoDB Cluster, or `mysql.wsrep_cluster_members` / `performance_schema.pxc_cluster_view` for Galera/PXC). Group Replication actions require `GROUP_REPLICATION_ADMIN` or `SUPER`; Galera actions require `SUPER`; MySQL Shell AdminAPI actions use the cluster administrator account across members. When the account lacks a required privilege, the disabled action shows the exact `GRANT` statement to copy (`Run it as an administrator, then Refresh.`). Suggested schema `GRANT`s use the account and wildcard setting (`partial_revokes`) read together in one login; schema names containing underscores or percent signs are escaped when needed so the suggestion grants access only to the named schema, and if that setting cannot be read, the action explains why it could not build a `GRANT`.

See the [Replication, clusters and proxies how-to guides](howto-topology.md) for walkthroughs.

## ProxySQL

**ProxySQL** connects to a ProxySQL Admin interface (port `6032` by default) to inspect backend servers, connection pools, hostgroups, monitors, query routing rules and query digests, and to apply reviewed runtime and disk changes.

- **What you see**: a summary line, findings when a hostgroup has no `ONLINE` server or backends are `SHUNNED`, metric tiles (**Backends ONLINE**, **Hostgroups**, **Query rules active**, **Client connections**), a **Configuration of servers** or **Configuration of query rules** status bar comparing `main` (memory) against `runtime` and `disk`, and five sub-tabs:
  - **Topology**: the connection group bar and a multi-tier routing diagram on a lit stage with floating server cards linking ProxySQL hostgroups to Readyset cache tiers and MySQL or MariaDB backends (with **Open Readyset**, **Open Cluster** and **Open Replication** links beside their rows, **Use `<connection>`** on cards matched to a saved connection in the group, link labels beside the connecting stems, and detached cards for `OFFLINE_HARD` backends; links animate only when ProxySQL reports a runtime `ONLINE` row outside a monitor's offline hostgroup, configuration-only rows and unreported states read **Not read**, and `SHUNNED` (including `SHUNNED_REPLICATION_LAG`) or offline-hostgroup servers stay stopped while a shunned writer card notes `standby ONLINE` when its backup writer is `ONLINE` in runtime; motion turns off with your system's reduced-motion setting, and `ⓘ` explains what it shows).
  - **Servers**: each backend in runtime and configuration (`Server`, `Hostgroup`, `Role`, `Status`: `ONLINE`, `SHUNNED`, `OFFLINE_SOFT`, `OFFLINE_HARD`, `Weight`, `In use`, `Free`, `Errors`, `Queries`, `Ping`). Selecting a server opens the inspector with its runtime status, connection pool counters, configuration row in `mysql_servers`, and any Galera, Group Replication, replication or Aurora monitor managing its hostgroups.
  - **Hostgroups**: each hostgroup's role, state (`OK`, `Watch`, `No ONLINE server`, `Empty`), server counts by status, total queries and connections used.
  - **Query rules**: rules from `mysql_query_rules` with `Rule`, `Active` (noting when memory and runtime differ), `Matches`, `Destination hostgroup`, `Apply`, `Hits` (with a `No hits` pill when zero), `Digests` (how many of the top 100 digests by total time the rule matches), and `Comment`. The inspector lists the matching digests and offers **Show its digests in Query digests**.
  - **Query digests**: queries `stats_mysql_query_digest` in Admin with **Order digests by** / **Order** (**Slowest**, **Most time**, **Most frequent**, **Highest rate**, **Most rows sent**), **Top** (**10**, **25**, **50**, **100**), **Search digest text**, **Hostgroup**, **Schema** and **User** filters. Each row shows both **Ran on** (the hostgroup where the digest actually executed, or `-1` for the query cache) and **Rules send to** (where the active `runtime_mysql_query_rules` route that digest, evaluated by myflames, flagging any `Mismatch` in watch amber).
- **Actions**: ProxySQL keeps three configuration layers: memory (`main`), `runtime`, and `disk`.
  - Row changes in the inspector edit memory and load to runtime in one reviewed unit: on a backend server, **Set ONLINE…**, **Set OFFLINE_SOFT…** (omitted when a Galera monitor manages the hostgroup, because the Galera monitor overrides `OFFLINE_SOFT`), **Set OFFLINE_HARD…**, **Change weight…**, and (when no monitor manages the hostgroup) **Move to hostgroup…**; on a query rule, **Enable rule…** and **Disable rule…** (`UPDATE ...` followed by `LOAD MYSQL SERVERS TO RUNTIME;` or `LOAD MYSQL QUERY RULES TO RUNTIME;`). If other unapplied changes already wait in memory for that module, row changes pause until you load memory to runtime first so `LOAD` never applies unreviewed rows.
  - Module-level persistence in the configuration bar (and offered as the next step after a row change): **Load servers to runtime…**, **Save servers to disk…**, **Load query rules to runtime…**, and **Save query rules to disk…** (`SAVE MYSQL SERVERS TO DISK;` / `SAVE MYSQL QUERY RULES TO DISK;`). Nothing is written to disk without its own review.
- **Account notes**: a stats-only ProxySQL account can read `stats` tables (connection pools and digests), while reading `main`, `runtime_*` and `disk` configuration tables and running changes requires an Admin account.

See the [Replication, clusters and proxies how-to guides](howto-topology.md) for walkthroughs.

## Readyset

**Readyset** connects to a Readyset SQL listener (port `3307` by default) or admin SQL listener (port `6036` by default) to inspect multi-tier caching topologies, active shallow and deep caches, uncached proxied queries, replicated base tables and runtime parameters.

- **What you see**: a summary line (showing **port not read** if the listener role could not be proved, and **caches not read** if `SHOW CACHES` failed), expandable **Findings** (**Problem** and **Watch** items, worst first, including missing `Status` or `Replication Status` fields so a report with missing data is never **OK**, with **Details** / **Hide details** and **Show in `<tab>`** to jump to the matching tab), metric tiles (**Cached share** and **Shallow hit rate**, which show **No traffic yet** when counts are zero or **Not read** when statistics were not read, **Active caches**, which reads **Not read** when `SHOW CACHES` failed, and **Base replication**, which names any replication error regardless of status, **Not replicating** when stopped, **Tables not read** when `SHOW READYSET ALL TABLES` failed with no lag, or **Not read** when status was not reported), and five sub-tabs:
  - **Topology**: the connection group bar, a multi-tier routing and CDC diagram on a lit stage with floating server cards across ProxySQL, Readyset and upstream MySQL or MariaDB servers, cluster peers and async replicas (with **Open ProxySQL**, **Open Cluster** and **Open Replication** links beside their rows, **Use `<connection>`** on cards matched to a saved connection in the group, link labels beside the connecting stems showing `Replication error` on any reported replicator error regardless of status, `Replication stopped`, `Replication disabled · query fallback` when disabled, `CDC replication` only when running without errors, or `Replication not read` when unreported, links animating only on a reported `Running` or runtime `ONLINE` state, down active CDC upstreams and problem peers drawn detached, configuration-only ProxySQL rows, unknown active CDC roles, fallback CDC host health without host data, and unreported states reading **Not read**, peer cards showing **Verified connection** only on a server UUID match and **Matched by address** for host-and-port or channel-source matches, motion turning off with your system's reduced-motion setting, and `ⓘ` explaining what it shows), plus the **Active client connections** table. Selecting an upstream card opens the inspector with its **Endpoint**, **Purpose**, **Active CDC**, **Health**, **Pool connections**, **Database**, verification evidence (**Verified** or **Matched by address**), and **Use `<connection>`** when matched.
  - **Caches**: active shallow (TTL and refresh) and deep (incremental streaming dataflow) caches with **Executions**, **Cached p50**, **Cached p99**, **Hit rate** (or `Materialized` for deep caches) and **Query** (showing **Caches not read** and omitting the tab count when `SHOW CACHES` fails). Selecting a cache opens the inspector with its cached SQL, configuration (TTL, refresh period, coalesce window, transaction routing properties), shallow cache efficiency (**Hit rate**, **Hits / Misses**, **Background refreshes**, **Wasted / Dropped**, **Coalesced waits**, **Upstream time saved**), and latency percentiles (**Cached execution latency** and **Upstream fallback latency**).
  - **Proxied**: observed queries from `SHOW PROXIED DEEP QUERIES` and `SHOW PROXIED SHALLOW QUERIES` (or `SHOW PROXIED QUERIES` on older Readyset releases) with **Filter proxied queries**, **Uncached only**, execution counts, upstream p50/p99 latency, and `EXPLAIN CREATE CACHE` support verdicts for both **Shallow** and **Deep** caching.
  - **Tables**: base tables tracked by Readyset's CDC replicator (`SHOW READYSET ALL TABLES`, showing **Tables not read** and omitting the tab count when the read fails) with table status (`Initializing`, `Snapshotting`, `Compacting`, `Creating index`, `Online`, `Not replicated`, or `Dropped`; a `Not replicated` table whose description starts with `"An unexpected replication error occurred:"` is flagged as an error) and replication metadata (**Replication**, reporting `Running`, `Stopped`, `Disabled`, or **Not read**, **Mode**, **Consume lag**, **Heartbeat**).
  - **Parameters**: **Operational state & credentials** (**Maintenance mode**, which records `Maintenance Mode` in memory as a signal for tools such as ProxySQL to stop sending queries while Readyset still serves what it receives; entering it is offered only when **Status** is `Online` because Readyset shows `Maintenance Mode` only once its snapshot finishes, and a Readyset restart clears the flag, and **Cached upstream privileges**), **Dynamic runtime parameters (ALTER READYSET)** (**Tracing log level**, **Eviction memory limit**, **Eviction check period**), **Shallow cache allowlists** (**Allowed SQL functions**, **Allowed session/global variables**, **Allowed schemas**; these filter only automatic shallow cache creation, while explicit `CREATE SHALLOW CACHE` and query hints are not affected), and **Admin port lifecycle (port 6036)**.
- **Actions**: every cache DDL, replication command or `ALTER READYSET` change stays visible in its action group (disabled actions remain focusable and show the reason and fix beneath the button, while another connection's report, a failed read, paused reads, or a read-only connection disables all actions with one line) and goes through a reviewed confirmation sheet:
  - **Caches and Proxied**: **Create cache…** (disabled while `SHOW CACHES` is unread because collision checks need the cache list) opens the **Configure Readyset cache** dialog, where you enter a SQL query or Readyset query ID (`q_…`), click **Check support (EXPLAIN)** to run a dry-run `EXPLAIN CREATE CACHE` check for both shallow and deep caches and check for cache collisions, choose **Cache type** (**Shallow cache (TTL & refresh)** with **TTL (seconds)**, **Refresh every (s)**, **Coalesce (ms)** and **ADAPTIVE refresh scheduling**, or **Deep cache (streaming dataflow)** with **Build deep cache CONCURRENTLY without blocking reads**), set **Cache name (optional)** and **Explicit transaction routing** (**Server default**, **ALWAYS (serve inside transactions too)**, **UNTIL WRITE (serve until first write in tx)**), and click **Review CREATE CACHE…**. **Export SQL** runs `EXPLAIN ALL CACHES` (falling back to `EXPLAIN CACHES` on older Readyset releases) so you can copy the DDL or click **Download .sql**; exports start with a `charset utf8mb4` line when runnable SQL or an emitted `USE` statement contains a non-ASCII character immediately before a backtick or backslash, so import them with the `mysql` or `mariadb` client. You can also choose **Flush entries…** or **Drop cache…** in a cache's inspector, **Flush shallow caches…**, **Drop all caches…**, **Drop shallow caches…**, or **Drop deep caches…** in the **Caches** tab, and **Clear proxied queries…** in the **Proxied** tab. Reported names keep exact spaces and backticks (table names are parsed once); a cache whose reported name contains a dot (`DROP CACHE` and `FLUSH CACHE` take a name only, so a dot is ambiguous), a name containing control or format characters, or a name that cannot be quoted has its row actions disabled with a fixed reason, review text shows control characters as visible escapes, typed confirmations warn when a name starts or ends with a space, and every change is re-checked from a fresh read before planning and sending so a cache (whose name and query ID must still match the same row), table or allowlist item that changed since it was read is refused instead of acting on the wrong row.
  - **Tables**: **Start replication…** or **Stop replication…**, **Set replication position…** (to set a GTID set or binlog `file:offset`), **Add tables to replicate…** (comma-separated `schema.table` names), and in a table's inspector **Re-snapshot table…** (disabled on that row if its name contains control or format characters or cannot be quoted).
  - **Parameters**: **Enter maintenance mode…** (enabled only when **Status** is `Online`) / **Exit maintenance mode…**, **Flush Readyset privileges…**, **Set log level…**, **Set eviction memory limit…**, **Set eviction period…**, **Allow…** / **Remove** on each shallow allowlist (**Allowed SQL functions**, **Allowed session/global variables**, **Allowed schemas**), and **Shut down Readyset…** (`SHUTDOWN`) and **Shut down & reset snapshot…** (`SHUTDOWN RESET`), enabled when connected to the admin SQL listener, disabled with the listener requirement on the SQL adapter listener, and disabled when the listener role could not be confirmed.
- **Port and listener notes**: myflames determines whether a connection reaches the SQL adapter listener (port `3307` by default) or the admin SQL listener (port `6036` by default) from query behavior rather than port numbers (`CREATE CACHE` and `EXPLAIN CREATE CACHE` require the SQL adapter listener with an upstream database schema selected; `SHUTDOWN` and `SHUTDOWN RESET` require the admin SQL listener; when Readyset does not show which listener the connection reaches, those actions stay disabled with `"Readyset did not show which listener this is."`). Readyset does not report in advance that a listener refuses cache DDL (`SHOW CACHES` and the other reads succeed there, admin listener sessions always allow cache DDL, and `EXPLAIN CREATE CACHE` is not affected), so myflames usually cannot disable cache DDL and allowlist actions ahead of time: Readyset refuses the statement when it is sent and the review result shows the refusal. When a read itself reports a cache-DDL restriction, cache DDL and allowlist actions stay disabled ahead of time with `"Run cache changes on the CACHE_DDL_ADDRESS listener or the admin SQL port (default 6036); CREATE CACHE still needs an upstream database selected."` (myflames never probes with a write, and Readyset does not gate these actions with SQL `GRANT` privileges).

See the [Replication, clusters and proxies how-to guides](howto-topology.md) for walkthroughs.
